PoC: Differential Sanitizer Behavior

Finding: Output mismatch between DOMPurify, sanitize-html, and js-xss

Category: Sanitizer behavior differential (medium severity)

Summary

Three HTML sanitizers handle the same malicious inputs differently:

Sanitizer Strategy MathML/SVG Custom Elements Semantic HTML
DOMPurify 3.x Allowlist (permissive) ALLOWS Strips ALLOWS
sanitize-html Allowlist (restrictive) STRIPS Strips STRIPS
js-xss Entity-encodes unknown ESCAPES Escapes ESCAPES

Test Case 1: MathML Content

Input:

<body onrejectionhandled="alert(document.cookie)">
<math>
<msup><mi>x</mi><mn>2</mn></msup>
</math>
</body>

Risk: DOMPurify preserves <math> elements which increases parser-differential attack surface. If the math content is later processed by a different parser (XML vs HTML5), namespace switching can enable mXSS.

Test Case 2: Semantic HTML with Event Handlers

Input:

<body onpagehide="alert(1)">
<details open>
<summary><em>Content</em></summary>
<custom-element popover="manual" hidden></custom-element>
</details>

DOMPurify: Strips event handler, preserves <details>/<summary> structure

sanitize-html: Strips everything, only text survives

Risk: DOMPurify's permissive approach preserves more HTML structure that could be leveraged in subsequent parsing steps.

Implications

  • Defense-in-depth failure: If an application switches sanitizers (e.g., migration from DOMPurify to sanitize-html), previously-stored sanitized content may contain elements the new sanitizer would have rejected.
  • Parser differential attacks: Elements preserved by DOMPurify (especially MathML/SVG) create namespace-switching opportunities for mXSS when content is re-parsed by different engines.
  • Content Security Policy bypass: Preserved HTML structure can be leveraged for CSS injection, data exfiltration via form elements, or UI redressing even without JavaScript execution.
